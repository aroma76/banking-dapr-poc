📌 In Plain English: What Am I Supposed To Do?

Here is the simple, jargon-free guide on what this project is, what you do each day, and what you show to your senior (Rajeev Ranjan).

1. The Big Picture (What is this project?)
You have a Bank Withdrawal System with two separate services:
  • Transaction Service: Accepts withdrawal requests from the user/Postman.
  • Accounting Service: Only this service can touch the database. It checks the balance, locks the account row, and subtracts money.
  • Dapr: Connects the two services without typing in hardcoded IP addresses or ports.
2. The Two Real Problems You Solve
  • No Negative Balance (Race Condition): If someone has ₹5,000 and two withdrawals of ₹3,000 happen at the exact same second, the database locks the row. First succeeds (₹2,000 left), second is rejected. Balance never drops below zero!
  • No Double Deductions (Idempotency): If network retries the same request twice, the system recognizes the request ID and returns the cached answer instead of charging twice.

  • Sep 25: Present the working demo to your senior and sign off!
4. What You Show In The Demo (Sep 25)

🐳 Docker Breakdown — The 6 Containers Parted Out

The system runs in Docker Compose as 6 lightweight containers connected on the bridge network banking-net:

# Container Name Tech / Image Port Network Mode Purpose & Working Mechanism
1 banking-postgres PostgreSQL 15 Alpine 5432 banking-net Single database. Stores accounts (balances) & withdrawal_transactions (audit). Seeds ACC001 (₹5,000) on startup.
2 dapr-placement daprio/dapr:1.13.0 50005 banking-net Dapr runtime directory router. Lets sidecars discover each other dynamically without hardcoded IPs.
3 transaction-app Spring Boot (Java 17) 8081 banking-net Microservice 1: Client entry point. Validates withdrawal request, then calls Dapr sidecar on localhost:3500.
4 transaction-dapr daprio/daprd:1.13.0 3500 service:transaction-app Sidecar for Microservice 1: Shares network with transaction-app, intercepts calls to accounting-service.
5 accounting-app Spring Boot (Java 17) 8082 banking-net Microservice 2: Owns PostgreSQL. Runs row lock (SELECT ... FOR UPDATE) and deducts balance safely.
6 accounting-dapr daprio/daprd:1.13.0 3501 service:accounting-app Sidecar for Microservice 2: Shares network with accounting-app, forwards received calls to localhost:8082.
💡
Key Docker Trick — Sidecar Network Sharing (network_mode: service:...):
Instead of giving each Dapr sidecar its own network, each sidecar shares the exact network stack of its Spring Boot app. This means transaction-app calls http://localhost:3500, and accounting-dapr forwards to http://localhost:8082 locally!

🔄 How Microservices Communicate — Step-by-Step Evolution

Step 1: Direct HTTP (Starting Baseline)
First, we connected the services using standard Spring RestTemplate:
POST http://accounting-app:8082/api/v1/accounting/withdraw

Why we did this first:
  • Proved the withdrawal calculation, JSON payloads, and PostgreSQL updates worked.
  • Zero extra dependencies needed for the first baseline test.

Drawback: Tight coupling! Transaction Service had to know accounting-app:8082.
Step 2: Upgrading to Dapr Service Invocation
Once direct HTTP worked, we switched to Dapr Service Invocation:
POST http://localhost:3500/v1.0/invoke/accounting-service/method/api/v1/accounting/withdraw

What changed:
  • Transaction Service only needs to know the app-id accounting-service.
  • Dapr handles service discovery, routing across containers, and retries.
  • Zero hardcoded hostnames or ports in Java code!
Feature Step 1: Direct HTTP (Initial) Step 2: Dapr Invocation (Final POC)
Target Address http://accounting-app:8082/... (hardcoded) http://localhost:3500/v1.0/invoke/accounting-service/...
Service Discovery Manual Docker DNS / container name Handled automatically by Dapr runtime
Coupling High (caller knows callee's port & host) Zero (caller only knows logical app-id)
Resilience / Retries Must write custom Spring retry code Built into Dapr sidecar automatically

🔒 How Concurrency Protection Works (Easy Beginner Explanation)

⚠️ The Problem: Simultaneous Requests (Race Condition)
Suppose Account ACC001 has a balance of ₹5,000.

Two withdrawal requests for ₹3,000 arrive at the exact same millisecond. If we don't lock the account:
  • Both requests read balance = ₹5,000 at the same time.
  • Both conclude there is enough money and deduct ₹3,000.
  • Final balance becomes -₹1,000! (Double spending bug).
✅ The Solution: Database Row Locking (SELECT ... FOR UPDATE)
We use @Lock(LockModeType.PESSIMISTIC_WRITE) in Spring Data JPA:
  • Request 1 begins and PostgreSQL locks the row for ACC001.
  • Request 2 arrives but must wait in line until Request 1 is done.
  • Request 1 deducts ₹3,000 (balance becomes ₹2,000) and commits.
  • Request 2 now reads balance = ₹2,000, sees ₹3,000 is not available, and is safely rejected!
The balance never drops below zero!
